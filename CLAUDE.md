# CLAUDE.md — рабочий контекст проекта Fixpoint (бывш. «Стенограф»)

Этот файл — память проекта для Claude Code при работе с любого компьютера. Здесь решения и планы, которых не видно из кода. Обновляй его при существенных изменениях курса.

## Что это

PWA-фотодневник ремонта: несколько объектов (квартир), редактор схемы квартиры, фото каждой поверхности по этапам, слайдер «до/после». Владелец — vvana (личный проект с прицелом на коммерциализацию). Общение с пользователем — на русском; пользователь предпочитает автономную работу без промежуточных подтверждений.

## Ключевые решения и их причины

- **PWA, а не React Native/Flutter** (сентябрь 2026): нулевой барьер установки, камера+IndexedDB покрывают все нужды, быстрая итерация. Код пишется так, чтобы позже безболезненно упаковаться в сторы: **Android — TWA (PWABuilder/Bubblewrap), iOS — Capacitor**. Перенос данных между PWA и упакованным приложением — через встроенный экспорт/импорт JSON.
- **Vanilla JS без сборки** — на машине пользователя нет Node (есть Python 3.14 для локального сервера). Не вводить сборщики/фреймворки без явного запроса.
- **Service worker — network-first с `cache: 'no-cache'`** (ревалидация). Не менять на cache-first: браузерный HTTP-кеш уже дважды приводил к «застреванию» старой версии.
- **Данные только на устройстве** (IndexedDB, фото как Blob, сжатие до 1600 px). Это осознанная позиция privacy: на сервер ничего не уходит. Страховка от потери — кнопка резервной копии.

## Модель данных (IndexedDB `stenograf`, v1)

- `projects {id, name, created}`
- `rooms {id, projectId, name, pts:[[x,y,r?],…], wallIds:[…], labels{wallId→имя}, created}` — многоугольник в метрах, до 10 вершин (`MAX_CORNERS`); третий элемент вершины — радиус скругления угла (м). `wallIds[i]` — стабильный id стены от `pts[i]` к `pts[i+1]`; у мигрированных прямоугольников это `n/e/s/w` (старый формат `x,y,w,h` конвертируется в `normalizeRoom` при загрузке). Удаление вершины сливает две стены: фото и проёмы переезжают на оставшуюся. Редактор: углы по умолчанию 90° (подтяжка при перетаскивании), угол и длину стены можно ввести числом (`setCornerAngle`, `setWallLength`).
- `stages {id, projectId, name, ord, status}` — status: 0 не начато / 1 в работе / 2 готово
- `photos {id, projectId, wallKey, stageId, blob, note, created, calib?, marks?}`
  - `calib`: `{type:'quad', pts:[4×[x,y]], w, h}` (углы стены по часовой от верхнего левого, метры) или `{type:'ruler', a, b, len}`; координаты точек нормированы 0..1 к натуральному размеру фото
  - `marks[]`: `{id, type:'dim'|'text'|'path'|'point', layer:'main'|'draft', ...}`; `point.kind` из `MARK_KINDS` (socket, switch, light, tv, water, sewer, heat, other)
- `rooms` дополнительно: `ceil` (высота потолка, м; по умолчанию 2.7), `openings {side: [{kind:'door'|'window', w, h}]}`
- `projects.calc` — настройки калькулятора материалов; работы по стенам — `walls: [primer|plaster|putty|paint|glass|wallpaper|tile]` галочками и по полу — `floors: [screed|waterproof|level|tile|laminate|board]` + `screedMm`, `levelMm`, по потолку — `ceils: [drywall|primer|plaster|putty|paint]` (с 2026-10-05; старые `wall`/`floor`/`ceil` читаются через `calcWalls`/`calcFloors`/`calcCeils`; пусто — «Не трогаем»)
- `projects.plan` — подложка схемы: `{blob, w, h, k, ox, oy}` (картинка, её размер в px, метров на px, положение левого верхнего угла в мировых метрах). В бэкапе blob уезжает как `data` (dataURL)
- **wallKey** = `roomId:side`, где side ∈ `n|e|s|w` (стены, экранные «верхняя/правая/нижняя/левая») или `c` (потолок) / `f` (пол). У комнаты 6 поверхностей.

## Дорожная карта «измерения и разметка» (утверждена пользователем 2026-09-05)

Идея пользователя: фото помещений должны стать рабочим документом — с размерами, пометками и точками для мастеров. Порядок, каждый шаг опирается на предыдущий:

1. Импорт фото из галереи (множественный) + дата съёмки из EXIF — сценарий «снял на стройке, разобрал вечером».
2. Калибровка фото: «4 угла стены + её размеры» (гомография, работает и для снимков под углом) или «рулетка в кадре» (2 тапа + длина). После калибровки любой отрезок на фото пересчитывается в реальные см.
3. Слои разметки поверх фото: размерные линии, текстовые заметки, наброски пальцем, типизированные точки (розетка, выключатель, светильник, вода, канализация…). Слой «черновик» удаляется одной кнопкой. Разметка — вектор, хранится отдельно от фото.
4. Экспорт «Задание для мастеров»: по комнатам и стенам фото с вжатой разметкой + таблица точек с высотами/отступами; «Поделиться» картинками и печать в PDF.
5. Проёмы (двери/окна) и высота потолка в редакторе → калькулятор площадей и расхода материалов.
6. «Призрачный слой»: старое фото с разметкой полупрозрачно поверх живой камеры (getUserMedia) — увидеть, где под штукатуркой кабель.
7. *(только нативная версия, отложено)* настоящее AR-совмещение (ARKit/ARCore), обмер лидаром/RoomPlan.
   - **«Обход этапа» (идея пользователя 2026-09-09, главная фишка нативной версии):** после каждого этапа пройти по квартире с телефоном — ARKit знает положение камеры относительно уже обмеренной схемы, кадры снимаются автоматически при стабильном виде на стену и сами привязываются к стене и этапу (никакой ручной привязки фото). Заодно лидар замечает изменения геометрии (новая перегородка, короб, ниша, потолок) и предлагает обновить схему; сравнение обмеров между этапами — контроль ровности/толщины. Полный текстурный 3D-скан этапа — только как бонус (тяжёлый, низкая детализация), фото остаются основным носителем.
   - **Фишка для лидара (пользователь просил запомнить, 2026-09-05): замер фактических размеров помещения** — обход комнаты с iPhone Pro (RoomPlan) даёт готовый план со стенами и размерами; эти размеры автоматически становятся схемой (pts/wallIds) и «фактическими» длинами стен, с которыми потом сверяются фото-измерения и калькулятор. На Android — ARCore Depth, точность ниже. Делать после упаковки в Capacitor.
8. Упрощение создания плана (сделано 2026-09-05): подложка из скана/фото плана БТИ с калибровкой масштаба по двум точкам и обводкой комнат тапами по углам; размеры при создании комнаты; мастер «обход по стенам» (длина → угол → длина…). Автовекторизацию скана и фотограмметрию по обычным фото отвергли (ненадёжно / невозможно в браузере).

Про точность, обсуждено: лидар iPhone ±1–3 см (1–2%), рулетка на фото 2–5%, лазерный дальномер ±2 мм — для раскроя материалов нужен дальномер, лидар/фото — для планирования. Нейросетевую оценку глубины по фото отвергли (ошибка 10–20%).

## Виртуальный тур (решение 2026-09-09)

1. **3D-тур из схемы и фото (сделано, `tour.js`, three.js r170 в `vendor/`, офлайн):** «кукольный домик» — стены как плоскости с последним фото поверхности для выбранного этапа (фото с калибровкой по 4 углам выпрямляется гомографией и ложится на стену «в лоб», без калибровки — кадрируется), пол/потолок по bbox, переключатель этапов (фото этапа или последнее с предыдущих), режимы «Домик» (орбита, потолки скрыты) / «Внутри» (из центра комнаты, осмотр пальцем) / «360°». Мини-план — переходы между комнатами.
2. **Панорамы 360° (сделано):** поверхность `roomId:p` — обычные фото по этапам; снимаются штатной камерой в режиме «Панорама» (частичный обзор: считаем vfov 65°, hfov по пропорции) или 360-камерой (пропорция 2:1 = полная сфера). Просмотр в туре.
- **Зеркала (сделано 2026-09-09):** проём вида `mirror` в `room.openings[wallId]` — `{kind, w, h, x, y}` (x — отступ от левого угла *как видит зритель изнутри* = совпадает с «от левого угла» на калиброванном фото; y — от пола). В туре зеркало — `Reflector` из three.js (настоящее отражение сцены, отражения снимающего нет). Двери/окна с позицией тоже рисуются в туре. Площадь зеркала из стен не вычитается. Для лидара (нативная версия): фантомная «комната за зеркалом» отбрасывается по обмеренному контуру; снимать зеркала под 30–45°. **Автоопределение зеркал** (обсуждено 2026-09-09) — как подсказка с подтверждением, не автоматика: признаки — «дыра» в плоскости стены + объём за ней внутри контура квартиры, зеркальная копия комнаты (пол на той же высоте, в отличие от окна), человек с телефоном в RGB-кадре этой области. Размеры/положение зеркала берутся из «дыры». Не работает для зеркала во всю стену при первом обмере и для полупрозрачных/глянцевых поверхностей — там ручная отметка.
3. **На потом — «финальный результат»:** полный текстурный 3D-скан лидаром (как Polycam) делается один раз в конце ремонта как витрина готового объекта (для заказчика и портфолио мастера); по этапам не нужен — тяжёлый, текстуры мутные. Нативная версия.

## Командная работа (обсуждено 2026-09-09)

Сценарий пользователя: «один iPhone Pro на бригаду» — прораб один раз обмеряет/рисует схему, рабочие снимают стены любыми телефонами, электрик видит на фото, куда ставить розетки, и отмечает сделанное. Этапы:
1. **Сделано (2026-09-09), без сервера:** обмен файлами через «Ещё → Команда объекта»: «Отправить схему» (kind `plan`, килобайты), «Отправить объект с фото» (kind `photos`), «Импорт» со слиянием (`importData`): plan/backup перезаписывают схему и этапы, фото никогда не удаляются; photos-файл от участника только добавляет новые фото/пометки и статусы «сделано», локальную схему не трогает. У фото и пометок есть автор (`by`, имя из localStorage `stenograf.user`), у точек — `done/doneBy/doneAt`. Отчёт фильтруется по специальности (`tradeOf`: электрика / сантехника / прочее).
2. **Следующий шаг — сервер синхронизации:** приглашение по ссылке/QR, роли владелец/рабочий, офлайн-очередь загрузки фото. Рекомендация — VPS в РФ + S3 (Selectel/Yandex), чтобы рабочие открывали без VPN; альтернатива Supabase. Решение по хостингу за пользователем. Это же — первая коммерческая точка (подписка «объекты с командой»); одиночный локальный режим сохраняется.
3. **Нативная iOS-версия — начата 2026-09-09 (пользователь скоро получит iPhone Pro):** `native/` — Capacitor 6 + локальный плагин `native/plugins/stenograf-roomplan` (Swift: `RoomPlanPlugin` → `RoomScanViewController` с RoomCaptureView; методы `isSupported`, `scan({mode:'measure'|'walk'})`). Swift отдаёт «сырые» стены/двери/окна (центр, оси, размеры, концы в плане X,Z; `parent` у проёмов) и в режиме walk — кадры стен (JPEG base64, углы стены в кадре TL/TR/BR/BL, снятые при стабильной камере, ≤2 на стену). Вся «умная» часть в JS (`native.js`): сборка многоугольника из отрезков (`scanToPolygon`, по часовой), проёмы «от левого угла» (`scanOpenings`), совмещение скана с существующей комнатой поворотом+сдвигом с учётом дверей/окон против симметрии (`alignScanToRoom`), перенос id стен/фото/зеркал при переобмере (`applyScan`), автопривязка кадров с автокалибровкой quad (`framesToPhotos`). Комнаты с обмером помечены `room.measured='lidar'` (📡 на схеме). Сборка: `.github/workflows/ios.yml` — macOS-раннер, `cap add ios` на лету, iOS 17.0, неподписанный ipa артефактом; установка Sideloadly. **Сборка на CI успешна с run #5 (2026-09-09): Swift компилируется (единственная правка — разбить длинные simd-выражения из-за type-check timeout), `Stenograf-unsigned.ipa` ≈1 МБ; артефакт `Stenograf-unsigned-ipa` в Actions → последний run, хранится 30 дней, пересобирается каждым пушем; лог xcodebuild тоже выкладывается артефактом. Шаг сборки строгий: ошибки компилятора печатаются в лог шага, ipa < 1 МБ = провал.** Нативная работа плагина на живом устройстве ещё не проверялась — первый тест на iPhone Pro пользователя. Дальше: многокомнатный обход (StructureBuilder), автоопределение зеркал, сервер синхронизации.
   Старый план: Нативная iOS-версия (Capacitor + плагин RoomPlan) — после сервера; сборка на GitHub Actions (macOS-раннер), установка через Sideloadly с бесплатным Apple ID (7 дней), позже TestFlight с аккаунта друга-издателя. У пользователя **iPhone 17 Pro** (лидар, A19 Pro, 48 Мп; iOS 26/27), Mac нет. Установка: Sideloadly (iTunes ставится вместе с ним, веб-версия — нужна именно она, не из Microsoft Store), на iOS 16+ обязателен «Режим разработчика», подпись 7 дней.

## Заход 2026-09-14: пять отложенных фич (по просьбе пользователя — всё сразу)

- **«Стереть» (PWA, `annot.js` → `eraseRegion`)**: кисть 🩹 в редакторе фото, режимы «заплатка» (заливка от границ + сглаживание) и «размытие»; оригинал хранится в `photo.original` (в бэкапе `originalData`), «⋯ → Вернуть оригинал».
- **Многокомнатный обход (Swift mode `multi`, `final`)**: одна ARSession на все комнаты (`RoomCaptureView(frame:arSession:)`, `stop(pauseARSession:false)`), кнопки «Следующая / Завершить», в конце `StructureBuilder` (fallback — сырые комнаты, они уже в общих координатах). JS `applyStructure`: поворот к сетке по доминирующему углу стен (`dominantAngle`), совмещение с существующим планом (4 поворота × центроид), переобмер комнат по близости центров, новые — добавляются; `wallMap` для кадров обхода всей квартиры. Кнопка 🏢 в шапке схемы; «🚶 Обход этапа» умеет «всю квартиру подряд».
- **Автоопределение зеркал (Swift `detectMirrors`)**: вершины ARMeshAnchor-ов «за» плоскостью стены (0,3–4 м) в сетке 10 см → связные плотные области ≥0,25 м и ≥0,15 м² → кандидаты с `parent`-стеной, центром и `fromFloor`. JS `proposeMirrors` спрашивает подтверждение на каждый.
- **AR-призрак (Swift mode `ghost`)**: старое фото + его калибровочный quad передаются в плагин, `pollGhost` ищет стену тех же размеров, проецирует углы (`ARCamera.projectPoint`) и накладывает UIImageView через гомографию → `CATransform3D` (`ScanMath.swift`); ползунок прозрачности. В PWA остаётся ручной призрак (`viewGhost`).
- **Финальный скан (Swift mode `final`)**: ключевые кадры 320px при сдвиге >0,35 м / повороте >20° (≤70), при «Завершить» — все mesh-якоря, цвет вершин из лучшего кадра (лицевая нормаль, расстояние), бинарный PLY base64 → `project.finalScan {blob, transform, vertices, faces}`; в туре режим «🏁 Финал» через PLYLoader (`vendor/`).
- **Тур «как на плане» (`tour.js`)**: по картинке пользователя — толстые белые стены (BoxGeometry, толщина 0,12 м снаружи контура, кремовая «крышка»), вырезы под двери/окна (дверь — створка, окно — стекло), цветные полы по комнатам (`FLOOR_COLORS`), освещение (Hemisphere + Directional, Lambert). Фото на стенах — переключатель 📷 (в режиме «Внутри» всегда включены).
- **CI-сборка #7 зелёная (2026-09-14)** — весь новый Swift компилируется (одна правка: построение сетки вынесено из UIViewController из-за main-actor). **Не проверено на устройстве**: всё Swift выше. Риски: `RoomCaptureView(frame:arSession:)` и повторный `run` на общей сессии; наличие ARMeshAnchor в сессии RoomPlan (если их нет — зеркала и финальная сетка вернутся пустыми, приложение это переживёт); `projectPoint` и обрезка viewport в RoomCaptureView; размер base64-PLY через мост (при >30 МБ подумать про файл).

### Точки съёмки на схеме (2026-10-04)
Кадры обхода лидаром хранят `photo.shot = {x, y, ang, h, ref}`: положение камеры на схеме (м), направление взгляда (рад, в координатах схемы), высота камеры над полом, `ref` — центр комнаты в момент съёмки (если комнату сдвинут в редакторе, точка рисуется со сдвигом центра). ### Стороны света (2026-10-07)
При обмерах (measure, walk, multi, final) Swift читает компас (`CLLocationManager`, `headingOrientation .portrait`). На каждом опросе берётся направление камеры в мире сессии и вычисляется север: atan2(z, x) − heading. Направление камеры берётся только почти горизонтальное, при точности компаса ≤ 30°. Значения усредняются по кругу, в результат идут `north` (рад, мир сессии), `northTrue` и `northSamples` (нужно ≥ 5).
Истинный север — при разрешённой геопозиции (в CI добавлен `NSLocationWhenInUseUsageDescription`, в podspec — CoreLocation), иначе магнитный.
JS `saveNorth` переводит север в оси схемы (угол схемы = угол мира + turn; для квартиры и финала — `results[0].place.turn`) и пишет `project.north {ang, true, n, at}`. На схеме слева внизу стрелка «С» (`#plan-north`); она поворачивается вместе с видом (`planView.r`).
**Не собрано и не проверено на устройстве.** Главный риск: при вертикальном положении телефона `CLHeading` должен давать направление задней камеры. Если стрелка окажется повёрнута, проверить знак и ось.

## Как работать

- Локальный предпросмотр: `python -m http.server 8787 --directory .` (или конфиг в `.claude/launch.json` соседнего уровня).
- Тестовые данные удобно сеять напрямую в IndexedDB через консоль (`dbPut(...)` — глобальные хелперы из `db.js`); после проверки — удалять.
- Деплой = `git push` в `main` (Pages обновляется сам). **iOS-сборка — только вручную** (с 2026-09-27, просьба пользователя «не собирать после каждой корректировки»): копить правки, собирать, когда пользователь попросит или когда набралась законченная порция и он готов ставить: `gh workflow run ios.yml`, дождаться run, скачать артефакт `Stenograf-unsigned-ipa` → `Desktop/Fixpoint.ipa` (с 2026-10-04; раньше `Stenograf.ipa`).
- Логи упавшей iOS-сборки читать через расширение Claude in Chrome (у пользователя стоит; в браузере бывает залогинен аккаунт ReKeyLab — переключать на vvana) или через артефакт `xcodebuild-log`.
- Правки файлов делать точечно (python-скрипты замены / Edit), после правок — перезагрузить вкладку дважды (SW network-first + HTTP-кеш python-сервера).
